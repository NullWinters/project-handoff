# OpenCode 实现说明

记录在 OpenCode v2 上实现该技能时，与官方文档不一致、只能靠实测确认的行为，以及据此作出的设计选择。

## 计数事件的选择

压缩计数订阅 `session.compaction.ended`，只在事件的 `reason` 为 auto 时递增。取消中断的压缩不计数，因为该事件只在压缩成功结束时发出，中断的压缩不会产生它。上游 Python 版本用的是 Codex 的 PostCompact 钩子，属于触发即计，可能把中断的压缩算进去。实测中一个在压缩过程中被终止的会话计数保持为零，与此选择一致。

## 回合结束信号

文档与类型定义中的 `session.idle` 事件不会出现在插件的事件订阅流里。逐个记录订阅流的事件类型后确认，可用的回合结束信号是 `session.execution.succeeded`，它携带会话编号。最终提醒的核验改在该事件到达时进行。

插件订阅流中的事件不按会话隔离，是当前位置下所有会话的广播。每个事件带 `session.data.sessionID`，消费端须按它过滤，否则会把别的会话的压缩计入当前会话。

## storage 的作用域

`ctx.storage` 是全局单例，作用域只按 key 前缀划分，不按位置、插件编号或插件路径划分。两个不同编号、不同位置、不同路径的插件实例只要使用相同前缀就会共享数据。因此分会话隔离只能依靠 `handoff:state:` 加会话编号组成的键结构。更换插件编号或安装目录都不提供隔离。

这一结论同时意味着会话移动到另一个目录后计数不会丢失：会话编号不变则键不变，storage 又不分区，状态自然延续。原计划中的文件兜底方案因此取消。

## 上下文注入

`ctx.session.hook` 的 context 钩子中，向 `event.system` 追加文本即可注入到模型上下文。注入每次模型调用都会生效，常态下只注入一行计数，到达评估点或存在未展示建议时才注入完整规则，控制开销。

注入内容的验证不能依赖模型复述。实测中模型会从对话历史复制上一轮的注入文本，给出过期结果。可靠的验证方式是让工具直接返回注入函数的输出，绕开模型。

## 工具与状态

四个工具 status、evaluate、prepare、respond 的参数校验分为两层：枚举值由工具的输入 schema 在执行前拦截，其余规则在工具逻辑内判断。prepare 的成功取决于冷却、去重、阶段、受益等条件，返回 `prepared` 与拒绝原因，模型据此调整。

工具不需要模型传入会话编号。`context.sessionID` 由宿主注入，比让模型填写更可靠。同理，回合身份取自 prompt 钩子事件的 messageID。

## 计数与实际状态的偏差

storage 计数与会话消息历史是两个独立的持久层。用户回退会话时间线时消息被撤销，但 storage 中的计数不回退，两者从此不再同步。偏差的方向是计数偏高，会使评估提前到来；评估本身还要满足安全位置、明确后续、切换收益三项条件，因此不会仅因计数偏高就误提醒。计数只覆盖插件加载之后发生的压缩，旧历史不回填。

## 事件归属的已知异常

实测中主会话的文本事件曾出现在同位置另一个分叉会话的观测记录里。该异常只影响调试用的观测数据，不影响计数，因为计数依据的是压缩事件的会话编号，三个会话的计数始终各自对应。生产实现删除了观测记录，此问题不再暴露。
