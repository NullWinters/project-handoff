# 计数、评估与最终核验

仅在插件注入 project-handoff 计数、需要登记评估或建议、或配置与排查计数器时读取。什么时候该提醒以 [SKILL.md](../SKILL.md) 为准，本页只讲登记方式、核验机制与实现边界。

## 计数与检查点

插件订阅会话的自动压缩事件，每次成功的自动压缩使计数加一。手动压缩、恢复会话、聊天轮数都不计数；同一回合可以发生多次自动压缩。被中断的压缩不计数。计数只覆盖插件加载之后观察到的事件，旧任务不回填。子会话的压缩不计入。

计数到达提醒点、且没有用户静默或指定节点时，插件在下一轮模型调用注入完整评估规则，需要一次评估。评估后在同一压缩点不重复查问；进入新的真实压缩会重新打开。业务阶段和用户指定节点由模型识别，插件不扫描历史、不猜阶段。

常态下插件只注入一行计数与冷却点；到达待评估的检查点、存在未展示的建议、用户静默或指定节点时，才注入完整规则。

## 登记工具

插件注册四个工具，均由宿主注入会话编号，模型不传。调用前读取工具说明中的参数。

| 场景 | 工具与参数 |
| --- | --- |
| 暂缓 | `evaluate`，outcome 为 defer，note 写明具体缺项，next_check 取 next_turn 或 next_compaction |
| 不适用 | `evaluate`，outcome 为 skip，note 写明纯问答、无后续或讨论本技能 |
| 首次次数提醒 | `prepare`，reason 为 count，附 stage_key、notice、safe、has_next |
| 阶段提醒 | `prepare`，reason 为 stage，另加 benefit |
| 已核实的新混淆 | `prepare`，reason 为 confusion，另加 cause_key、benefit |
| 用户指定节点到达 | `prepare`，reason 为 checkpoint，另加 checkpoint_key |
| 用户确认完整交接 | `respond`，response 为 handoff，附 proposal_id |
| 用户说先不交接 | `respond`，response 为 continue，附 proposal_id |
| 用户指定节点 | `respond`，response 为 defer，附 proposal_id 和 checkpoint_key |
| 静默／恢复 | `respond`，response 为 mute 或 resume |

`prepare` 返回 `prepared` 与拒绝原因。只有 `prepared` 为真才能在最终答复首段展示。常见拒绝原因：冷却未到、阶段重复、缺收益、notice 格式不合、静默或等待用户节点。被拒绝时先核实原因，再登记暂缓或不适用。

约束：note 不超过 160 字，不存用户原文或敏感信息；notice 是 20 到 600 字的一段话，以“交接建议：”开头，不能换行；safe、has_next、benefit 必须有事实依据。登记暂缓或不适用会关闭尚未展示的旧建议。

`status` 返回当前会话的完整状态，用于排查。

## 最终核验

展示没有人工回执入口，进度消息里出现过建议也不登记。插件在会话回合结束时读取最终答复的首段，跳过引用和代码块，与当前建议原文比对，一致才计一次正式提醒并开始冷却。文本核验不等于用户已经看到。

首段未出现建议时，下一轮注入会带一次补漏指令；再错过就标记为未展示并关闭该建议。同一建议的重复结束事件不重复计数。

## 实现边界

插件在会话的事件订阅流中处理回合结束。该流是当前位置下所有会话的广播，按事件中的会话编号过滤，因此不同会话的计数互不影响。

storage 是全局单例，只按 key 前缀划分。分会话隔离依赖 `handoff:state:` 加会话编号。更换插件编号或安装目录都不提供隔离，两个实例使用相同前缀会共享数据并造成重复计数，因此同一位置不能同时存在两个实例。

计数与会话消息历史是两个独立持久层。用户回退会话时间线时消息被撤销，计数不回退，两者从此不同步。偏差方向是计数偏高，会使评估提前；评估本身还要满足安全位置、明确后续、切换收益三项条件，不会仅因计数偏高就误提醒。

插件不联网、不调模型、不新建业务任务。正常检查不增加模型轮次，只有漏评估或漏展示时才会触发一次补漏。
